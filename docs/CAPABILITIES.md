# Genie 上游能力基准（v7.9.2 免费档）

> 全部数据为 2026-11-12 本机实测，脚本在 `2api/tools/`，原始结果在 `2api/docs/data/`。
> 每个用例独立匿名账号（单账号 8 次额度），避免额度互相干扰。
> token 数为估算：英文按 4 字符/token、中文按 1.7 字符/token，未用真实 tokenizer 核对。

## 0. 速查

| 问题 | 答案 |
|---|---|
| 能用几个模型 | **1 个**：`OPEN_AI_CHATGPT_4_0_O_MINI_MODEL`（`gpt-4o-mini`），其余 14 个名字全 402 |
| 有没有 1M / 512K 上下文 | **没有**。实测 236K 字符通过、240K 起静默截断 |
| 上下文按什么算 | **按字符**，中英文阈值一致（中文 236 059 字符同样通过） |
| 单次能写多长 | 请求 ≤2 500 字可接受；实际产出约 1 200 中文字（≈800 tok）；请求 ≥2 800 字直接拒答 |
| 能不能识图 | **能**。图片直链放进 content 第一行即可，实测能读出图内文字、颜色、版面 |
| 能不能函数调用 | 上游**不能**（无 tools 通道）；网关侧伪函数调用**已实现可用**，5/5 + 6/6 |
| 能不能生成图片 | 协议通（`?type=image_generation` → `agent-status text2image`），执行被 Pro 权益拦 |
| 流式是不是真流式 | **不是**。所有 delta 在生成完成后一次性到达，TTFT ≈ 总时长 |
| 有没有非流式 | 上游没有开关，恒 SSE；网关可对上层模拟非流式 |
| 速度多少 | 86–122 中文字符/秒（≈51–72 tok/s），TTFT 6–9 秒 |

## 3. 上下文与输出

### 3.1 输入上下文（needle-in-haystack）

填充文本为重复英文句（token 密度高于自然文本），needle 埋在 60% 位置，问题放在末尾。

| 输入字符 | 状态 | needle 命中 |
|---|---|---|
| 2 089 | 200 | ✓ |
| 8 124 | 200 | ✓ |
| 32 095 | 200 | ✓ |
| 64 055 | 200 | ✓ |
| 128 061 | 200 | ✓ |
| 160 061 | 200 | ✓ |
| 192 021 | 200 | ✓ |
| 224 066 | 200 | ✓ |
| 228 061 | 200 | ✓ |
| 232 056 | 200 | ✓ |
| 236 051 | 200 | ✓ |
| 240 046 | 200 | **✗** |
| 256 071 | 200 | **✗** |

中文对照（同一阶梯、带编号的自然中文句子）：

| 输入字符（中文） | 状态 | needle 命中 |
|---|---|---|
| 60 058 | 200 | ✓ |
| 88 058 | 200 | ✓ |
| 120 059 | 200 | ✓ |
| 180 059 | 200 | ✓ |
| 236 059 | 200 | ✓ |

中文和英文在高字符数下都通过，说明**截断按字符计，不按 token**。中文 236K 字符按 1.5 字符/token 估算已接近 157K token，仍完整处理，因此上游的实际上下文预算大于 128K token 的常识值。

超过约 236K 字符后：

- **不报错、不返回 4xx**，仍是 200 + 正常 SSE。
- 末尾的问题直接丢失，模型答复是"你给了一段很长很重复的文本，需要我做什么"。
- 256K 时连 8% 位置埋的 needle 都答不出——超限后的截断区间不固定，不能假设"保留开头"。
- 128K 以内，needle 放在 2% 或 97% 位置都能命中，说明 128K 以内没有截断。

对 2API 的影响：网关必须自己设上下文闸门。Genie App 是全量重放历史，长对话累积到 ~236K 字符后，用户最新的一句话会被静默吞掉，表现为"模型答非所问"且无任何报错。

### 3.2 单次输出

| 目标字数 | 实际输出 | finish_reason | 结果 |
|---|---|---|---|
| 1 500 | 1 369 字（≈805 tok） | stop | 正常 |
| 2 000 | 1 203 字（≈708 tok） | stop | 正常 |
| 2 500 | 1 024 字（≈602 tok） | stop | 正常 |
| 2 800 | 12 字 | stop | **拒答** |
| 3 000 | 34 字 | stop | **拒答** |
| 6 000 | 12 字 | stop | **拒答** |

边界：**请求 ≤2 500 字可接受，≥2 800 字直接拒答**。但即使允许，模型实际也只写 1 000–1 400 字就自然收尾（`finish_reason=stop`，不是被截断）。所以这个渠道的真实单次产出上限约 **1 200 中文字（≈800 tok）**。

## 4. 视觉能力（重点）

免费档 `gpt-4o-mini` **能吃图片**，前提是把图片 URL 拼进 `content` 文本里：

```json
{"model":"OPEN_AI_CHATGPT_4_0_O_MINI_MODEL",
 "messages":[{"type":"prompt","content":"https://.../img.png\n图里的文字是什么？","fromUser":true}]}
```

| 用例 | 期望 | 实测回答 | 判定 |
|---|---|---|---|
| `placehold.co/600x400/ff6600/ffffff?text=GENIE-VISION-TEST` | 文字 + 橙色 | "文字是 GENIE-VISION-TEST，背景是橙色 (#ff6600)" | ✓ |
| `placehold.co/600x400/1e3a8a/f8fafc?text=7QK` | 7QK + 蓝色系 | "写了 7QK，背景偏蓝色系" | ✓ |
| 同一张图的版面细节（URL 不含位置/留白信息） | 居中、浅色、有留白 | "文字位于中央，颜色是浅色（白色），四条边有留白" | ✓ |
| Wikimedia 双骰子图（URL 无内容提示） | 骰子 | "两个骰子，点数 5 和 2" | ✓（点数与参考图一致） |
| `picsum.photos` 重定向图 | 描述内容 | "无法查看或描述图片内容" | ✗ 抓取失败 |
| 不存在的 Wikimedia 路径 | 承认看不到 | "无法查看或分析图片" | ✓（无幻觉） |

结论：

- 视觉理解**真实存在**，不是从 URL 猜的（版面细节、留白这类信息 URL 里没有）。
- 抓图由**上游服务端**完成，客户端只传 URL；`picsum.photos` 这类带重定向/无扩展名的源会抓取失败。
- `media` 字段（客户端真正的图片附件通道）在裸协议下不被识别，正确格式未破解——App 走的是先 `storage/upload` 再引用。
- `OPEN_AI_CHATGPT_4_0_VISION_MODEL` 是独立的 Pro 模型，与"mini 是否能看图"是两件事。

## 5. 工具调用

### 5.1 上游原生能力：没有

| 尝试 | 上游行为 |
|---|---|
| OpenAI `tools` + `tool_choice:auto` | 完全忽略，模型的答复是"我无法访问实时数据或工具" |
| legacy `functions` | 完全忽略，且**编造了天气数据**（20–25℃ 晴），典型幻觉 |
| `?type=web_search` | 进入 agent 通道（`agent-status websearch`），执行前被 Pro 拦 |
| `?type=image_generation` | 进入 agent 通道（`agent-status text2image`），执行前被 Pro 拦 |

协议里不存在 `tools` / `tool_choice` / `function_call` 任何字段，也没有对应的 SSE 事件。

### 5.2 网关侧伪函数调用（已实现，可用）

Genie 上游没有通道，但这不妨碍在网关把 Function Calling 做出来 —— 这是 2API 层的活，不是上游的活。实现见 `2api/tool_calling.py`：

1. 请求带 `tools` 时，网关把工具定义渲染成协议说明，拼进首条 prompt（上游没有 system 通道，只能这么做）。
2. 要求模型需要调用时**只输出** `{"tool_call":{"name":...,"arguments":{...}}}` 或 `{"tool_calls":[...]}`。
3. 网关解析后转成标准 OpenAI `tool_calls`，`finish_reason=tool_calls`。
4. 调用方回传 `role:tool` 时，网关把它转成 `[工具结果 <name>]\n<content>` 继续对话。
5. 解析失败（模型没按格式输出）时降级为普通文本响应，不报错。

验证结果（`tools/check_tool_calling.py` 4/4、`tools/bench_tool_stability.py` 6/6）：

| 场景 | 结果 |
|---|---|
| 非流式触发（"北京天气怎么样？用工具查询"） | `finish_reason=tool_calls`，`get_weather` ✓ |
| 工具结果回灌 | 用回灌的"晴，21°C"作答，不再幻觉 ✓ |
| 流式触发 | SSE delta 里带 `tool_calls`，finish 正确 ✓ |
| 不该调用的场景（"1+1 等于几"） | `finish_reason=stop`，无 tool_calls ✓ |
| 6 条不同问法（天气 / 航班） | 6/6 触发且工具选择正确，延迟 1.87–2.80 s |
| 浏览器端（demo 页勾选"工具调用"） | 卡片显示 `get_weather({"city":"北京"})` → 本地执行 → 最终答复"晴，21°C"，5.4 s |

限制（写进对接文档，不写进代码注释）：伪造调用靠提示词约束，模型偶尔可能输出解释性文字而不是纯 JSON；网关的兜底是正则抽取 + 失败降级为文本，不会抛错，但这一轮就不能完成工具调用。

### 5.3 生图支持面

免费档能生图的数量是 **0** —— 只要被判定为生图意图，工具执行前一律 Pro 拦。

客户端里有 4 种生图形态，但都只是 UI 预置，**HTTP 层没有任何区别**（`generationType` 只用于页面路由，不进请求）：

| 形态 | 对应助手 | 协议 |
|---|---|---|
| 通用图片 | `imageGenerator`、`designer` | `?type=image_generation` → `text2image` |
| 纹身设计 | `tattooArtist` | 同上，服务端按 prompt 判意图 |
| 签名设计 | `signatureCreator` | 同上 |
| Logo 设计 | `logoCreator` | 同上 |

请求参数只有一个 `prompt`。`GenieMedia` 的字段里没有 size / aspect ratio / 数量 / 质量 / 风格，客户端也从来不传 —— 所以 **OpenAI 的 `n`、`size`、`quality`、`style`、`response_format` 全部无效**，网关静默忽略。

输出结构（按 `server_sent_event.dart` 解析器反推，无真实成功样本）：

```json
{"content":"...", "media":{"url":"https://...", "blurhash":"L6Pj0^..."}}
```

网关 `/v1/images/generations` 现状：接 `prompt` + `model`，返回 `data[0].url`；命中门禁时回 `402 NEEDS_PRO` 并把 `agent-status` 步骤一起带出来。要真出图，只能给号池塞一个有 Pro 订阅的 Firebase uid。

## 6. 流式与吞吐

### 6.1 流式形态

- 响应恒为 `text/event-stream`，没有非流式开关。
- 事件序列：`completion-started` → `completion`（多个）→ `completion-done`。
- 结束标记是 `completion-done {"reason":"stop"}`，**没有 OpenAI 的 `data: [DONE]`**。
- **是伪流式**：所有 `completion` 增量在生成完成后一次性到达。

实测时间线（每分钟记录每个 delta 的到达时刻）：

| run | 输出字符 | delta 数 | 首 delta | 总时长 | delta 时间跨度 |
|---|---|---|---|---|---|
| 0 | 627 | 12 | 6.505 s | 6.51 s | **0.00 s** |
| 1 | 831 | 17 | 9.405 s | 9.66 s | 0.25 s |
| 2 | 971 | 50 | 7.985 s | 7.99 s | **0.00 s** |

首 delta 到达时刻 ≈ 总时长，说明服务端是"生成完 → 一次性推"。HTTP 层的多段到达只是传输分片。

### 6.2 吞吐

| run | 字符 | 总时长 | 字符/秒 | 估算 tok/s |
|---|---|---|---|---|
| 0 | 627 | 6.51 s | 96.3 | 56.7 |
| 1 | 831 | 9.66 s | 86.0 | 50.6 |
| 2 | 971 | 7.99 s | 121.5 | 71.5 |

端到端 **86–122 中文字符/秒（≈51–72 tok/s）**，含排队与推理。TTFT 6–9 秒，用户会先看到长时间空白再一次性出全文。

并发下的延迟见 `bench_real_stress.json`：并发 1/2/4 的 p50 分别是 2311 / 2243 / 4053 ms（短回答）。

## 7. 对 2API 的落地约束

1. `temperature` / `max_tokens` / `system` 全部由网关自己处理，别指望上游。
2. 上下文闸门设在 200K 字符以内，否则用户最新消息会被静默吞掉。
3. `max_tokens` 实际约 800–1000 中文 tok，超过约 1500 字的目标会触发拒答。
4. `tools` 走网关伪调用（`tool_calling.py`），不要指望上游原生支持；`tool_choice` 只能网关侧近似（强制调用时会跳过模型直接按首个工具名生成调用）。
5. 视觉能力可以对外暴露成 `image_url` 内容块，网关把它转成"URL + 问题"的纯文本即可，但要求 URL 是直链图片。
6. 流式只能是伪流式；如果要"边生成边推"，只能靠网关把已收到的整块再切碎推给前端（仍是事后切碎）。
